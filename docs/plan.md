# Project Plan

Project name: **Internity**

Internity is a lightweight intern management platform for onboarding interns, organizing departments, scheduling classes, assigning tasks, collecting submissions, and reviewing intern work. It is designed as a modern web application with a simple monorepo, Docker-first development, and GitOps deployment to a Linux VM running K3s.

## Recommended Name

Use **Internity**.

Why this name fits:

- It clearly describes the product domain.
- It covers the whole lifecycle: invite, onboard, learn, submit, review.
- It sounds simple and professional.
- It works well as an app name, repository name, Docker image prefix, and Kubernetes namespace.

Suggested repository slug:

- `internity`

Suggested Docker image names:

- `dockerhub-username/internity-frontend`
- `dockerhub-username/internity-backend`

Other possible names:

- InternDeck
- MentorDesk
- CohortFlow
- SkillTrack
- TraineeHub

## Product Overview

Internity will support five roles:

- Admin
- HR
- Supervisor
- Instructor
- Intern

The system should make it easy to:

- create and manage departments
- invite interns by email
- activate intern accounts with secure onboarding links
- assign supervisors and instructors to departments
- schedule classes with external meeting links
- publish assignments
- receive intern submission links
- review submissions with scores and written feedback
- draft assignment text, rubrics, and class agendas for supervisors and instructors
- keep users scoped to the departments and permissions they are allowed to access

## MVP Scope

## Repository Direction

Use one simple monorepo for the first version.

The detailed notes mention dedicated frontend and backend repositories. That can work later, but for this stage a monorepo is easier because:

- frontend and backend changes can be reviewed together
- shared UI and types can live in one place (`packages/ui`)
- CI/CD is easier to understand at the beginning
- Docker Compose can run the whole project from one repo
- Argo CD manifests can live beside the app until the deployment process is stable

If the project grows, split into three repositories later:

- `internity-frontend`
- `internity-backend`
- `internity-gitops`

## Role Summary

Admin:

- manages HR accounts
- has full user oversight
- can override departments
- manages system-level configuration
- can revoke access and reset accounts

HR:

- creates departments
- assigns supervisors
- assigns instructors to departments
- sends intern email invitations
- views organization directories

Supervisor:

- manages instructors in their assigned department
- can act as an instructor
- can view department interns, classes, and assignments
- can draft assignments, rubrics, and class agendas inside their assigned department
- cannot manage other departments

Instructor:

- schedules classes
- creates assignments
- drafts assignments, rubrics, and class agendas inside their assigned department
- reviews submissions
- provides scores and feedback
- stays scoped to assigned department

Intern:

- activates account from email invitation
- views department dashboard
- views classes and assignments
- submits external links with notes
- views feedback and grades

## AI Drafting

Supervisors and instructors can ask the backend to fill two forms. Admin, HR, and intern accounts cannot call these routes. A supervisor is limited to their own department, the same boundary as when they act as an instructor.

The browser sends the person's short description. The backend checks the session, loads department data itself, calls Groq, and returns a structured draft. The form stays editable. The existing assignment and class save actions are what create or update the record. A draft is not stored as an assignment or a class on its own.

`qwen/qwen3.8-27b` is a Groq preview model. Keep the model id in backend config so a later Groq id is a single change. Groq documents thinking and instruct modes for this model. These two drafts use instruct mode: `reasoningEffort: "none"` and `reasoningFormat: "hidden"`.

Both calls use the Vercel AI SDK on the backend:

- packages: `ai` and `@ai-sdk/groq`, installed with pnpm in the backend app
- client: `groq` from `@ai-sdk/groq`, which reads `GROQ_API_KEY`
- call: `generateText` with `output: Output.object({ schema })`
- schema: Zod, validated before the response leaves the backend
- no tools, no browser search, and no image input

`GROQ_API_KEY` lives in the backend env file, which stays gitignored, and later in the backend Kubernetes secret. The frontend bundle must not contain it. If the key is empty, drafting returns a clear error and the rest of the app still runs. Log the user, department, and feature name. Do not log the API key.

### Assignment and rubric drafter

Used from the assignment editor.

The client sends a short learning goal. The server may include the department name from the session. It does not trust a department id sent by the browser.

The response fills:

- title
- instructions
- rubric criteria, each with a name, a description, and a point value
- a suggested deadline the person can change

The assignment remains Draft until the person publishes it through the normal assignment action.

Route: `POST /api/instructor/ai/assignment-draft`

### Class agenda drafter

Used from the class scheduler.

The client sends a short description. It may also send an assignment id. The server loads that assignment only when it belongs to the caller's department, and it may include the previous class title and agenda from that department.

The response fills:

- title
- agenda

The person still enters the date, time, and external meeting link.

Route: `POST /api/instructor/ai/class-agenda-draft`

Supervisors call these same instructor routes. The handlers use the existing instructor permission check, which already allows a supervisor inside their own department.

## Dashboard UX Direction

Internity should feel like a practical operations dashboard, not a marketing site. The full specification lives in `docs/dashboard-design.md`. Tokens, icons, motion, and the component inventory live in `docs/design-system.md`.

One shell serves all five roles:

- topbar with the department switcher, a ⌘K command menu (`@beui/command-palette`), the theme toggle (`@beui/theme-toggle`), and the user menu
- left navigation built on beUI's `@beui/ai-sidebar`, adapted into a navigation tree with Phosphor duotone icons and a collapsed icon rail
- one content template: page header, KPI row, panels
- detail surfaces as `@beui/drawer` on desktop and `@beui/bottom-sheet` on mobile

Patterns by screen:

- role-specific home screen with compact KPI cards (`@beui/animated-number` values)
- department tables, intern rosters, and submission review tables on `@beui/table` and `@beui/table-async`
- status shown as `@beui/animated-badge`, never color alone
- class schedule timeline with the agenda in `@beui/bouncy-accordion`
- assignment editor and class scheduler whose AI draft action fills the fields, which the person then edits and saves through the normal action
- clear empty, loading, error, and success states on every surface

Component sourcing is beUI first: install `@beui/*` slugs from the live registry (`https://beui.dev/r/registry.json`) with pnpm, swap their lucide icons for Phosphor duotone, and cover the rest with shadcn components on Base UI primitives in `packages/ui`. No third-party dashboard templates.

Interface copy follows one voice: sentence case, verb-first buttons, errors that name the fix beside the field that failed.
